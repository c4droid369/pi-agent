# Minimal Change

## 何时用
- **极简实现**（默认）：新功能、bugfix、小重构，需要控制复杂度 → 用「可砍清单」
- **精准修改**：用户要求「精准修改」「只改这里」「别动别的」、生产紧急修复、范围必须严格限制 → 用「改动定位」
- 不适用：架构设计阶段（归 design），除非用户明确要「极简实现」或「MVP 方案」
- 大规模重构或代码现代化时应关闭精准修改模式

## 通用底线
中文汇报、验证不得虚报、改动分级、破坏性 git 禁令见全局 `AGENTS.md`；这里只写比全局更具体的部分。
- 能 50 行搞定就不写 200 行；一次性代码不做抽象
- 需求没点名的特性、灵活性、可配置项概不加
- 可砍清单之外的东西，不得以极简或「只改这里」为名删除
- 删之前先搜调用点；涉及已有代码的删改需先获得同意
- 极简不等于不验证：无现成测试时至少跑类型检查与 lint

## 可砍清单（命中才砍）
- 不必要的抽象层：接口只有一处实现、泛型/配置从未有第二个使用点
- 过度参数化：参数从未被不同调用方以不同值使用
- 不可达分支：当前需求下某条件分支永远走不到
- 为不存在的场景兜错：不会发生的异常捕获、空值防御
- 重复造轮子：项目内已有等价实现的工具函数
- 从未被引用的导出函数、变量、常量

## 必须保留
- 用户明确要求的功能行为、边界条件处理、错误处理、已有调用方依赖的行为
- 可裁剪的只有：灵活性、可配置项、装饰性扩展、为「万一用得到」预留的接口

## 改动定位（防漏调用方）
1. 找到需求对应的改动点（函数、变量、配置项）
2. 追踪该改动点的所有调用方，确认调用约定（参数格式、返回值语义）不受影响
3. 评估是否影响外部依赖方（其他服务、持久化格式、API 契约）
4. 确认调用方不受影响后才动手
5. 改完重审 diff，确认只包含必要变更

## 清理范围
- 只清理因本次改动而不再被引用的孤儿导入、变量、函数
- 判断标准：本次改动前存在的引用已被移除，且代码库中无任何新引用
- 既有孤儿代码不主动删除，只提醒用户其存在

## 验证标注
- 紧急修复且无现成测试：至少跑类型检查与 lint，明确标注「此改动未被自动化测试覆盖，剩余风险为 X」
- 无法运行任何验证：说明原因和剩余风险，不声称验证通过

## 边界
- 砍功能不等于砍冗余：功能是用户要求的，冗余是代码自身多余的
- 已有代码超出必要复杂度时，先说明精简方案与理由，经确认后再动，不擅自推倒重来
- 因极简产生可预见债务，必须明确告知用户，由用户决定是否接受
- 不因「修复很小」跳过调用方追踪，生产事故多源于忽略调用约定

## 交付前自检
- diff 里没有可砍清单之外的多余改动
- 每个被删的符号都确认过没有调用方
- 未验证的部分已明确标注，没有含糊说「应该没问题」
