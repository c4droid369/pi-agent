# Clarify First

## 何时用
满足任一条件才启用，否则直接执行：
- 存在会导致方案分叉的未指明点（输入来源、边界行为、失败处理）
- 存在多种相互矛盾的理解，影响实现方向
- 信息缺口无法从代码、文档或已有上下文推导

## 提问规则
- 只问影响方案走向的问题；能自己查到的答案不问
- 按影响程度排序：方案选型 > 边界行为 > 细节确认
- 每个问题给出推荐默认值与理由：「我建议默认 X，因为……，除非你有其他考虑」
- 有多个选项时编号并各带一句推荐，末尾注明「直接回序号就行，也可以改条件或加约束」
- 一次抛完，不挤牙膏式追问

## 输出结构
1. 当前理解：一两句话复述需求，确认基线
2. 需确认的问题：编号列出关键问题（带默认值）
3. 暂定假设：未确认前按此推进的假设

## 用户回复后
- 确认默认值 → 直接采用，不重复确认
- 给出新信息 → 更新理解；若引入新的关键分叉点，补一轮简短确认
- 「你看着办」→ 按暂定假设推进，标注「此假设未确认」，交付时汇总为风险

## 结束条件
- 方案分叉点已收敛，剩余不确定性只影响实现细节
- 无法收敛时（如第三方 API 行为无文档），列出风险应对策略，不无限追问

## 常见坑
- 不为「问得专业」问用户不需要回答的问题，能用代码验证的就不问
- 默认值必须给理由，否则用户无法判断该默认值是否合理
- 「你看着办」不等于授权任意假设

## 交付前自检
- 每个问题都写了默认值和理由
- 没有能从代码/文档查到却被推给用户的问题
- 暂定假设在交付时被汇总成风险条目
