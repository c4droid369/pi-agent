# Diagnose

## 何时用
- **Bug 定位**：报错、行为异常、偶现失败、要找根因
- **性能调优**：跑得慢、响应慢、超时、瓶颈明确
- 不适用：没有症状的审查（quality-review）、预防性优化、架构级性能设计（design）

## 通用底线
中文汇报、验证不得虚报、改动分级、破坏性 git 禁令见全局 `AGENTS.md`；这里只写比全局更具体的部分。
## 共同原则（顺序不可跳）
1. 先复现或量化并记录基线；复现不了不猜，列出已尝试路径与缺失信息，或转埋点观测方案
2. 按证据强度定位，不凭感觉：日志/错误栈 → 二分法 → 边界 → 数据与状态；性能场景用 profiler 或链路日志
3. 定位到根因或热点后才动手；先写能稳定触发的测试或记录优化前基线
4. 一次只改一个点，改完立即复测，确认收益或修复生效后再继续
5. 修复后找同类代码，检查是否存在相同模式的其他位置

## Bug 复现
- 先问清三件事：触发条件、期望行为、实际行为；不清楚先澄清
- 最小化复现：简化输入、隔离环境变量、区分是数据问题还是代码问题
- 复现不了就不猜：列出「已尝试的复现路径」和「缺少的信息」，让用户补充，或转为埋点观测方案

## Bug 定位（按证据强度）
1. 日志/错误栈：错误信息、堆栈、日志中的异常模式
2. 二分法：按最近改动、功能演进、版本回退确定引入范围
3. 边界检查：输入边界、空值、并发状态、资源释放
4. 数据与状态：持久化数据、内存状态、外部依赖，确认异常出在哪一层

## 根因确认
- 先写能稳定触发的测试或脚本，确认失败
- 修复后重跑该测试确认通过，再跑相关回归
- 根因必须能解释所有症状，否则继续查

## 性能工序
1. 量化：确认症状可复现（压测/计时/日志），记录当前基线
2. 定位：用 profiler 或链路日志找到真正热点；找不到证据就说「当前信息不足，需要 xxx 数据」
3. 候选：每个优化点给出影响范围、预估收益、改动代价，按性价比排序
4. 小步：一次只改一个点，改完立即重测
5. 回归：跑相关测试与 lint

## 输出
Bug：复现步骤（最简可操作路径）→ 证据链（症状到根因）→ 最小修复及理由 → 验证结果（哪些通过、哪些未验证）
性能：基线数据 → 瓶颈定位（文件:行号 + 证据）→ 候选排序（收益/代价）→ 每步前后实测 → 剩余风险

## 与其他 skill
- 注入、越权、数据泄露的安全结论归 quality-review 的安全审计
- 回归测试怎么写归 testing-guidelines；修复范围原则归 minimal-change

## 交付前自检
- 有可复现路径或基线数据，不是「我觉得是这里」
- 根因能解释全部症状
- 临时加的调试代码/日志已移除
