# Testing Guidelines

## 何时用
- 编写测试、评审测试、制定测试方案、补测试、测试重构
- 不适用：判断是否必须补测试与补到什么程度（归 quality-review 的质量门禁）

## 分层策略
默认「先单元、后集成、端到端选择性」，不默认三层全做。
- 单元测试：单个函数/模块，隔离外部依赖，覆盖核心逻辑、边界条件、错误路径
- 集成测试：跨模块协作、数据库/外部接口/三方服务交互，覆盖核心业务链路
- 端到端测试：按项目规模可选，只覆盖用户关键旅程，不覆盖所有分支

## 设计与命名（六条）
1. 独立性：每个测试可单独运行，不依赖执行顺序或共享可变状态
2. 结构：Arrange-Act-Assert，三段之间空行分隔
3. 命名：`被测对象_条件_预期结果`，如 `createOrder_库存不足_抛异常`；集成测试可用 Given_When_Then
4. 断言：断言行为与结果，不断言实现细节（如内部调用次数），除非该调用本身就是被测契约
5. 依赖隔离：优先轻量真实依赖（内存数据库、测试文件、本地 HTTP Server）；必须 mock 的只有第三方服务、昂贵或不稳定依赖、环境无法构造的场景；只 stub 被测对象的直接依赖，不 mock 被测对象本身
6. 测试数据：内联构造优先；共享 fixture 只在多个测试真正复用同一结构时提取，改动时检查所有使用点

## 覆盖率与维护
- 不设硬性百分比，但核心业务逻辑与关键分支必须覆盖；边界条件、错误处理路径至少各有一个测试
- 重构时相关测试必须保持通过；产品逻辑未变而测试失败，优先修脆弱断言，不改产品代码
- diagnose 定位并修复的 bug，必须留一个能稳定复现的回归测试
- 新功能改变已有契约时，先更新受影响测试再实现，或同步修改

## TDD（可选）
- 仅当用户明确要求：先写失败测试 → 实现至通过 → 重构

## 通用底线
中文汇报、验证不得虚报、改动分级、破坏性 git 禁令见全局 `AGENTS.md`；这里只写测试特有的：
- 稳定、快速、结果可预期；依赖时间/网络/并发的测试标记 `[flaky]` 并隔离，不计入常规通过标准
- 失败先查测试本身（共享状态、随机性、环境差异），确认不是产品代码问题前不改产品代码
- 不为凑覆盖率写不验证行为的测试，也不过度 mock 导致测试绑死实现细节

## 交付前自检
- 新测试能单独跑通，且失败时错误信息能指出问题
- 覆盖了至少一个边界条件和一个错误路径
- 没有为通过而放宽断言，也没有 mock 掉被测对象本身
