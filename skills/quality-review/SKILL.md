# Quality Review

## 何时用
- **代码评审**（默认）：功能实现、bugfix、重构后的验收，PR/MR 合入前
- **安全审计**：对外接口、鉴权/权限模块、用户输入、三方依赖接入、上线前自查
- **质量门禁**：正式项目交付前，守住结构约束与验证底线、记录技术债
- 不适用：架构方案选型（design）、文档逐字校对；未完成模块只做阶段性检查，不出终审或「通过」结论

## 统一分级（所有模式共用）
- 🔴 严重：功能失效、数据错误、或可直接利用的安全漏洞，必须修
- 🟠 高危：大概率触发错误、特定条件下可利用、越权或敏感数据暴露，应尽快修
- 🟡 中危：一般问题、维护性欠佳、加固缺失、条件触发型风险，建议修
- 🟢 低危：风格、可读性、非关键性能优化、纵深防御建议，自行决定

## 通用底线
中文汇报、验证不得虚报、改动分级、破坏性 git 禁令见全局 `AGENTS.md`；这里只写比全局更具体的部分。
- 用户要求「帮我修」时给完整改后代码或最小修复补丁，并说明原因
- 每条问题定位到具体文件:行号或代码块，说清问题、原因、改法，禁止「建议优化一下」
- 不为「全面」而报无实质影响的问题，宁缺毋滥；不报未核实可利用性的理论风险
- 多个模式同时启用时输出一份报告，同一问题不重复展开

## 代码评审：四维关注点
- 正确性：空输入/超长输入/极端值、错误处理路径、并发访问、状态变更、异常分支是否幂等
- 性能：高复杂度循环、N+1 查询、重复计算、资源未释放；只报能量化或大概率有影响的
- 可维护性：重复代码、职责过重、命名是否表意、耦合度、依赖方向
- 可读性：控制流复杂度、长函数、魔法数字、嵌套层级

## 输出要求
- 按正确性 → 性能 → 可维护性 → 可读性审查，先抓功能错误与数据异常
- 同时指出值得肯定的写法，帮助作者巩固好习惯
- 代码量大时按模块分批，优先错误处理、边界条件、并发、外部输入等高风险路径
- 复评只复核改动过的部分；若改动影响其他模块逻辑，扩展到受影响调用方

## 安全审计
- 优先级：RCE/越权/数据泄露等直接可利用 → 注入、SSRF、XXE、反序列化、路径穿越 → 安全配置与信息泄露
- 每条给出：位置、漏洞类型、攻击场景（谁能打、怎么打、打穿后拿什么）、危害程度、修复方案
- 检查硬编码密钥、Token、数据库凭据、内网地址；依赖声明中有已知 CVE 的直接点明可升级版本
- 复现粒度：严重/高危给验证思路或 PoC；中低危给攻击场景与触发条件即可；PoC 只证明存在，不给可直接武器化的完整利用代码
- 有现成工具（npm audit / pip-audit / bandit / gosec / semgrep）先跑，结果只作线索，每条人工核实
- 工具覆盖不到的越权与业务逻辑绕过，以人工审计为主

## 质量门禁
- 结构约束：函数/文件过长先判断是否真影响可读性；项目有规范按项目，无规范时 1000 行 / 300 行是提示线不是硬阈值
- 技术债：发现的存量坏味道只记录不修，格式为「位置、问题类型、影响、建议修复时机」
- 拆分方案：拆大文件属结构变更，先出方案（模块边界、函数归属、依赖关系），确认后再动手
- 是否补测试、补到什么程度由本模式判断；怎么写归 testing-guidelines

## 结论状态（与分级正交）
分级表示严重程度，状态表示确认程度，两者必须都写：
- ✅ 已确认：有 PoC、日志或可复现步骤支撑
- ⚪ 待验证：有推测路径但未证实可利用，或未跑过验证；**不计入「必须修」**
- ⛔ 已排除：查过并有排除理由（写清查了什么）

只写分级不写状态的一律视为「未审」。

## 审计范围与收尾
- 开审前列范围清单：要审的模块 / 文件 / 攻击面，以及本次明确不审的（附理由：不属代码审计范围、未启用路径、已知但本轮不处理）
- 停止判据（三条同时满足才能说「审完」）：范围清单全覆盖；每条结论都有状态；没有遗留的 ⚪ 待验证 未交待
- 修复后按影响面重审（改动的文件 + 直接调用方），不整仓重审
- 报告分四类：新增 / 仍存在 / 已修复且已复验 / 已修复未复验；「已修复未复验」必须进剩余风险

## 冲突取舍
- 正确性与可读性冲突：正确性优先，同时给兼顾可读性的改法
- 性能与可维护性冲突：默认可维护性优先，除非瓶颈已量化且严重影响体验
- 安全与功能冲突：严重/高危必须修，哪怕要改交互；中低危可与产品权衡后排期
- 与项目既有风格冲突：尊重存量风格，只提必要的一致性风险，不推广个人偏好
- 修复后无法重新验证时标注「修复未被验证，剩余风险为……」，不下「已修复」结论

## 交付前自检
- 每条问题都有 文件:行号 + 可执行改法 + 分级 + 状态
- 报告里没有「建议优化一下」这类空话
- 没跑过的验证明确标为未验证，没有把阶段性检查说成终审
- 要下「审完」结论时，能指出范围清单已全覆盖
