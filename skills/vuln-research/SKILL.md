# Vulnerability Research

## 何时用
- 目标是**外部项目**（不是你正在开发的代码）：挖洞、审攻击面、复现已知漏洞、判定影响面
- 不适用：自己项目的审计与交付门禁（quality-review）、明确报错的排查（diagnose）、没有源码或未获授权的目标

## 边界与授权（动手前先确认）
- 只在有权测试的目标上做：本地自有环境、自己克隆的源码、自建靶场或比赛环境；不碰别人的线上实例
- PoC 与 fuzzing 工程**仅用于验证漏洞存在，不做武器化**：不写完整利用链、不写绕过缓解措施、不打包成工具或平台
- **产出上限是「证明存在」**：若演进到需要武器化（可用利用链、绕过缓解、横向移动），必须另立授权流程并与本 skill 脱钩
- 披露按目标项目的 `SECURITY.md` / 披露政策：遵守其公开范围与等待期；没有政策时先联系维护者
- 漏洞出在第三方库 / 上游时，先报给对应维护者，不自行公开影响面
- 不把 PoC / 崩溃样本 / 细节发到公共 issue、论坛、仓库；对外共享前先确认允许范围
- 每轮记下授权依据（自建环境 / 开源源码 / 赏金范围）与测试时间窗，便于日后查证
- 分级与状态标签沿用 quality-review（🔴🟠🟡🟢 + ✅已确认 / ⚪待验证 / ⛔已排除），报告格式不另立一套

## 0 准备（每轮固定做）
- 固定版本：commit / tag / 构建哈希；所有结论必须绑定到具体版本
- 读 `SECURITY.md`、历史 CVE / 安全公告、最近的安全相关提交，避免重复别人已报过的问题
- 隔离：clone 到 `~/work/<项目>`，绝不在自己的项目树里构建或污染
- 先跑通构建与自带测试并记录命令与耗时 —— 后面所有复现都依赖它

## 1 攻击面建模
通用入口：解析器（文件 / 协议 / 序列化）、网络与 RPC、认证与授权、文件与路径、命令 / 模板 / 表达式求值、
依赖与供应链、配置与默认值、权限边界（提权、沙箱、跨用户、跨租户）。按项目类型加权：
- 系统 / 库类：内存安全、整数与长度、生命周期、ABI 边界、并发与信号
- Web / 服务类：鉴权与越权、注入（SQL / 命令 / 模板 / 头）、SSRF / XXE、反序列化、上传与路径穿越、限流与竞态
- 语言运行时：解释器与编译器边界、沙箱逃逸、资源耗尽、宏与求值时机
每条入口标「可达性」：需要什么前置条件才走得到（默认配置？已认证？特定输入通道？）

## 2 静态审计
按攻击面排序读，不按目录顺序；每个可疑点记录位置、验证假设、触发条件、状态（默认 ⚪ 待验证）。
不写「可能有风险」——要么给出可验证假设，要么不记；顺着数据流走：输入从哪来 → 经什么变换 → 在哪被信任

## 3 动态验证与挖洞工程化
手段按成本从低到高：定向构造输入 → harness 驱动目标函数 → 覆盖率引导 fuzz（libFuzzer / AFL 等）→ 差分测试
- harness 与种子放 `~/work/<项目>/fuzz/`，脚本可复跑、参数可配
- 崩溃先去重再判真伪，分诊与最小化按 `diagnose` 的调试取证执行；本 skill 只负责把它们记成 finding
- 记录编译器与 sanitizer 选项、种子、运行时长，保证别人可复现
- **工程化止步于「能稳定复现」**：不做持续挖矿基础设施，不累积可复用的攻击工具链

## 4 复现与最小化
- 最小 PoC：一条命令或一个输入文件，在干净环境可重复
- 对比 upstream 最新版 / 已修复提交，确认是老问题还是仍存在
- 区分「能触发崩溃」与「能造成安全影响」——前者只是线索

## 5 影响面判定（三问）
- 能打穿吗：读到什么 / 改了什么 / 能否执行代码
- 前置条件多苛刻：默认配置是否可用、是否需要已认证或本地访问
- 影响面多大：单进程 / 单用户 / 整机 / 宿主 / 多租户

## 6 交付
- 报告含：受影响版本范围、入口与前置条件、最小 PoC、复现步骤、影响面判定、修复建议
- PoC、harness、日志放 `~/work/<项目>/`，报告引用路径而不是把大段代码塞进会话

## 证据目录（以 finding id 为主键）
```
~/work/<项目>/
  recon/   版本 / 构建信息 / 攻击面清单 / 可达性表
  notes/   findings/<id>.md：假设、数据流、状态、待验证点
  poc/     <id>/：最小 PoC（输入文件或一条命令）
  fuzz/    harness、种子、语料、crashes/（未去重原始样本）
  logs/    构建与运行日志、sanitizer 输出（报告只引路径）
  report.md
```
- 一个 finding 一个 id，从 `notes/findings/<id>.md` 贯穿到 `poc/<id>/` 与报告条目
- 未去重的崩溃样本（`fuzz/crashes/`）与最小化 PoC（`poc/`）分开放；样本体积大，纳入版本控制要单独 `gitignore`

## 交付前自检
- 每个结论都绑定到具体版本与构建方式，每条都有状态
- 最小 PoC 能在干净环境复跑；⚪ 待验证 的数量与原因写清
- 没有越过「仅验证、非武器化」的边界
