# Project Onboarding

## 何时用
- 接手新项目、分析陌生代码库、进入大型遗留项目、定位一个模块的入口
- 不适用：已有明确上下文的小改动、纯代码评审与安全审计（quality-review）
- 用户目标能在不摸底的情况下直接完成时不启用

## 探索范围
- 先确认目标：了解整个项目，还是只需某模块/某服务的上下文
- 局部探索不摸全项目，输出聚焦该模块

## 摸底（按顺序；先跑命令再读文件，缺入口就跳过）
1. 项目内 AGENTS.md —— 最高优先，与全局冲突时按「边界与冲突」处理
2. README / 项目文档 —— 只读定位段落（构建、测试、架构），不逐字读
3. 依赖与技术栈 —— `package.json` / `Cargo.toml` / `go.mod` / `guix.scm` / `requirements.txt`，都没有再看 `Makefile`
4. 目录职责 —— `find . -maxdepth 2 -type d | sort`，不要一上来就读文件
5. 构建与测试入口 —— `make -n`、`make help`、`ls tests scripts`；CI 配置里的命令最权威
6. 规模与味道 —— `wc -l` 前十的文件、`rg -n 'TODO|FIXME' | head`
7. 活跃度 —— `git log --oneline -20`、`git log --stat -5 -- <核心目录>`
8. 文档可信度 —— `rg -n 'deprecated|outdated' docs | head`（文档常滞后于代码）

## 项目卡片字段
- 技术栈与关键依赖（含版本锁定情况）
- 常用命令（启动/测试/构建/lint）及来源
- 目录结构与核心模块职责，标注不确定项
- 测试状况：哪些模块有测试、哪些没有、当前能否跑通
- 风险：超大文件、无测试模块、复杂构建流程、过时文档
- 下一步建议：结合用户目标推荐优先探索的入口

## 信息冲突
- 文档与代码不一致：以代码实际行为为准，标注「文档与实现不符」
- 同一命令多种写法：以项目内 AGENTS.md 或 CI 配置为准

## 常见坑
- 只看顶层目录就下结论，核心逻辑常藏在子目录
- 跳过测试入口摸查，导致后续改动无法验证
- 假设依赖已装好；无法运行命令时明确说明「当前环境无法验证」

## 交付与交接
- 用一段话总结全貌，重点说与用户目标相关的部分，不只把卡片扔给用户
- 让用户确认卡片理解正确后再开始后续任务

## 交付前自检
- 每条常用命令都实际跑过或标明来源未验证
- 不确定项被显式标出，没有猜着填
- 卡片之外给了与用户目标相关的那一段总结
